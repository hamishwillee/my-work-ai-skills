# Shared rules

Read by every lens, before that lens's own file.
This holds what all lenses share: the read-only rule, scope, the new-or-changed gate, sources of truth, verification, and severity.

## Read-only

You are read-only with respect to the PR and GitHub: never modify a file as it exists in the PR, never push, and never run `gh pr comment`, `gh pr review`, `gh pr edit`, or any other write operation.
The one file you may create is the report itself, and only the main agent does that, only when the reviewer asks for it, and only outside the clone.

**One narrow exception**, for `tool-check.md` only: in PR mode it may create a disposable local git worktree and a scratch branch, purely to run the project's own `Tools/msg/generate_msg_docs.py` against the PR's committed content.
This never touches the PR itself, is never pushed anywhere, and must be torn down (`git worktree remove`, delete the scratch branch) before that lens returns.
In local or single-message-audit mode (`SKILL.md`, "No PR given") it instead runs the script directly against the reviewer's own working tree — nothing is created or torn down, since the generator only reads `msg/` and writes to its own scratch `-d` output directory.
No other lens touches the filesystem beyond reading.

## Scope

Only `msg/*.msg` and `msg/versioned/*.msg` files changed by the PR are reviewed.

- `msg/px4_msgs_old/**` holds frozen historic message versions. A PR touching one is a `bug`-severity finding on its own (these shouldn't change), not a naming/comment review — don't apply the naming or comment lenses to it.
- `docs/en/msg_docs/**` and `docs/en/middleware/dds_topics.md` are generated by `Tools/msg/generate_msg_docs.py`, never hand-authored. A PR that hand-edits one is a `bug`-severity structural finding; don't review it as prose.
- A non-`.msg` file changed in the same PR (`.cpp`, `.yaml`, build files) is never reviewed itself, but read it if it's relevant context (e.g. a publisher/subscriber change that explains a field's new purpose).

If no `msg/*.msg` or `msg/versioned/*.msg` file changed, say so and stop: this skill has nothing to review.

## New-or-changed determination

**This is the gate the naming lens and (partly) the comment lens run through, and it exists because a field's name and type are effectively part of a wire contract: renaming or retyping one breaks every publisher, subscriber, and logged `.ulg` that references it.
A naming or comment-necessity finding is only ever raised against something this PR is already touching in the relevant way — never as an unsolicited "by the way, this old field's name is bad."**

For every field and constant declaration in a changed `.msg` file's diff, classify it before applying any lens:

- **New.** The declaration is added (a `+` line with no prior declaration at that position). Naming and comment-necessity both apply in full — evaluate the name as if introduced fresh, same as any new field.
- **Renamed or retyped.** The diff replaces an old declaration with a new one at the same position, and the field/constant's *name or type token* differs between old and new (not just the trailing comment). Naming applies in full to the new name — judge it on its own merits, not as "different from the old name." Comment-necessity applies to the comment as it now reads.
- **Comment-only edit.** The name and type tokens are byte-identical between old and new; only the trailing `# ...` text changed. Naming does **not** apply — never suggest renaming a field whose name this PR didn't touch. Comment-necessity and grammar/spelling do apply, to the changed text.
- **Untouched.** The field/constant doesn't appear in any diff hunk, even though other lines in the same file changed. Out of scope for every lens. If `tool-check.md`'s run of the generator surfaces an error whose line number lands on an untouched declaration, that's a pre-existing issue — report it once, below the tables, per "What goes below the tables" in `SKILL.md`, not as a finding against this PR.

When a `.msg` file is renamed or newly added wholesale (not a same-file diff), every field/constant in it counts as **New**.

**Single-message audit mode overrides this section entirely** (`SKILL.md`, "No PR given" and "Single-message audit mode"): there's no diff to classify against, so every declaration in the audited file is treated as in scope, with `naming.md`'s findings capped at `minor` rather than gated out.

## Sources of truth

Listed in precedence order: a claim backed by a higher source outranks one backed by a lower source.

1. **The output of `Tools/msg/generate_msg_docs.py -e`**, run against the PR's own head SHA (see `tool-check.md`). This is the project's own validator — it's ground truth for anything it checks (units, `@enum` consistency, whitespace, missing summary, command-parameter shape).
2. **`references/style-guide.md`**, the written documentation standard, for anything the tool doesn't mechanically check (description structure, wording conventions, exemptions).
3. **Actual publisher/subscriber usage in `src/**`**, found by searching for `ORB_ID(<topic>)` (see `comments.md`, "Finding the actual publishers and subscribers"). This is what a message-level long description is checked against — not what the fields alone suggest the message is for.
4. **Internal consistency within the same PR** — do two fields/messages this PR touches document the same kind of thing the same way?
5. **Sibling messages elsewhere in `msg/`** — precedent for how a similar field/constant is named and commented elsewhere in the tree.
6. **`references/community-conventions.md`** — maintainer norms from real review history, applied at `style`/`minor` only, never `bug`, and never above the written standard.
7. **This skill**, last on purpose: everything above it is published and reviewable, `SKILL.md` and these references aren't.

Where two genuinely contradict each other, report the contradiction instead of picking a winner.

### Reaching the sources

- **PR diff, description, linked issue**: `gh pr view`, `gh pr diff`, `gh api`.
- **A local `PX4-Autopilot` clone**: check `~/github/PX4/PX4-Autopilot` and sibling common locations first. `tool-check.md` needs one to run the generator; `comments.md` needs one to search `src/**` for publishers/subscribers when checking a long description; the other lenses can work from `gh pr diff` alone but a local clone makes reading sibling messages (source 5 above) much cheaper than fetching them one at a time over the API.
- **Sibling messages**: read them from the same clone, or `gh api repos/PX4/PX4-Autopilot/contents/msg/<Name>.msg?ref=<base-sha>`.
- **Publisher/subscriber usage**: `grep` the same clone's `src/` tree — see `comments.md` for the exact recipe. There's no practical API-only fallback for this one; skip the long-description check rather than guess when no local clone is available.

## Verification

Every finding needs evidence you actually checked:

- **Tool-check**: quote the exact line the generator printed.
- **Naming/comments/style**: quote the exact rule from `style-guide.md` or `community-conventions.md` (with its link) and the offending text, and confirm the new-or-changed classification that put it in scope.
- **Long-description publisher/subscriber claims**: name the actual file(s) and module the `grep`/context search turned up, not just "seems to be published by X."
- **Grammar/spelling**: quote the offending text and the correction.
- **Line numbers**: match the head SHA's file. If you can't find the line by exact string match against the file as fetched, drop the finding rather than guess its location.

A finding that fails verification is dropped, not downgraded.

## Severity

| Severity | Meaning |
| --- | --- |
| `bug` | Violates the written standard or fails the project's own generator — the generated docs render wrong, missing, or misleading |
| `style` | Violates a named convention (style guide or a community-conventions rule cited at `style`) but the meaning survives |
| `minor` | No rule violated; a preference the author can decline, or a community-conventions rule explicitly marked contested/unsettled |
| `hint` | Grammar-only observation on a terse inline field/constant comment (see `grammar-spelling.md`) — never counted in the triage totals, listed separately |

`hint` exists because field/constant comments are meant to be terse; a grammar nit there is a suggestion, never something to block a PR over.
